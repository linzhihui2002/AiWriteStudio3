### 2.1 dsh 安装现状（实测）

| 项 | 值 |
|---|---|
| 版本 | `@deepseek-ai/dsh@0.1.0-rc.8`（rc 预发布） |

| profiles | 仅 `web` 一个（捆绑 9 个 bundle：dshmarket、mcp-manager、recall-plugin、vision-router 等） |
| 端口 | dsh web 默认 3080；用户另有本地代理占 3456 |
| 活跃度 | 本项目 AiWriteStudio3 已注册 6 个 dsh 会话（2026-09-13 起），**dsh 处于活跃使用状态** |

### 2.2 dsh 项目级挂钩机制（源码级确认，影响设计）

- **指令注入**：从"最近含 `.git` 的祖先目录"到 cwd 逐级读取 `AGENTS.md`/`CLAUDE.md`（+ `.local` 覆盖）；总预算 65536 字节（本机预设值）；单文件上限 1MiB。
- **技能发现**：`<projectRoot>/.dsh/skills`（rank 100，最高优先）> `.agents/skills` > customSkillDirs > `~/.dsh/skills` > `~/.agents/skills`；仅两层结构，`SKILL.md` 需 frontmatter（`name` kebab-case + `description`）。
- **dsh 核心不认识 `.harness/` 目录**（novel-harness 私有约定）；**无按项目加载 MCP 的机制**；无项目级 cordis patch。
- **`DSH_HOME` 可用环境变量重定向**（隔离方案的关键支点）。
- **项目根现已有 `.git`**：2026-09-19 初始化仓库后，工作台在项目根运行时可按该根发现指令与项目技能；第三方参考目录仍按各自边界处理。

## 3. DeepSeekHarness 冲突分析与隔离方案（重点章）

### 3.1 冲突面清单（逐项：本机证据 → 风险 → 措施）

| # | 冲突面 | 本机实测证据 | 风险 | 措施 |
|---|---|---|---|---|
| C1 | PATH 全局 `dsh` 命令 | `dsh.ps1` 在 `AppData\Roaming\npm`，全局 npm 0.1.0-rc.8 | 工作台误调 PATH 上的 dsh，受用户全局配置/版本影响，行为不可控 | 工作台**只调用内置 dsh 的绝对路径**（`workbench/vendor/dsh/node_modules/.bin/dsh`），代码层禁止裸 `dsh` 调用（lint 规则 + 启动自检） |
| C2 | `~/.dsh` 配置与凭据被污染 | 历史调研确认用户侧含独立配置与凭据 | 访问用户全局目录会破坏隔离边界 | 独立 `DSH_HOME`（3.2）；现行红线为**禁止读写**用户全局 `~/.dsh`；旧全局目录基线脚本不适用于现行流程（9.7） |
| C3 | 用户自定义 preset 与 profile | `.agent-presets/liangshen`、唯一 profile `web`（9 个 bundle） | 新增/修改 profile、preset 破坏"梁神模式"与 web 界面 | 内置 dsh 的 dsh-home 中**只建专用 profile**，不触碰用户 profiles；不用 `dsh plugin` 向用户环境装任何东西 |
| C4 | 端口冲突 | dsh web 占 3080；本地代理占 3456；novel-harness Studio 用 8765 | 启动失败或误连他人服务 | 工作台端口 **8790**，占用时明确报错，不自动顺延；不使用 3080/8765/3456 |
| C5 | projectRoot 解析歧义 | 第三方参考目录可能有独立 `.git` | 从错误目录运行会改变技能与指令发现范围 | 工作台根已初始化 `.git`；运行时固定项目根，第三方参考目录不作为工作台写入根目录 |
| C6 | 会话与 workspace 注册表刷写 | `~/.dsh/storages/workspace.json` 与 sessions 目录持续增长 | 自动化任务在用户 DSH_HOME 里刷出海量会话，污染用户界面与召回索引 | 独立 DSH_HOME 使 headless 会话记录全部落在 `.workbench/dsh-home` 内，用户侧零增长 |
| C7 | 模型配置与 API Key 串用 | 用户 settings.yaml 有明文 Key；本项目 `模型API.md` 也有明文 Key | 工作台误读/误改用户 Key；工作台 Key 泄入用户环境或导出文件 | 模型配置**单向投影**（6.4）；凭据安全规范（9.6）；显式导入用户 dsh 配置仅限非敏感字段且需人工确认（FR-MODEL-002A 继承） |

### 3.2 隔离架构（落地 FR-MODEL-000 系列）

```text
┌─────────────────────────────────────────────────────────────┐
│ 产品层（工作台自有 UI + 业务）：小说项目 / Story Bible /      │
│ 写作 / 审稿 / 工作流 / Token 仪表盘                          │
│   业务代码只依赖本项目 HarnessRuntime 接口，禁止触碰 dsh 内部  │
├─────────────────────────────────────────────────────────────┤
│ DSH Adapter（本项目 Python 模块）：Session/Agent/Task/Model   │
│   兼容接口、headless 进程管理、Provider 投影、Contract Test   │
├─────────────────────────────────────────────────────────────┤
│ 内置 dsh 运行时：workbench/vendor/dsh/（npm 本地安装，版本    │
│ 锁定 0.1.0-rc.x）+ .workbench/dsh-home/（独立 DSH_HOME）      │
└─────────────────────────────────────────────────────────────┘
        │ 环境变量注入：DSH_HOME=<项目>/.workbench/dsh-home
        │ 绝不读取/写入 C:\Users\30332\.dsh
```

硬性要求（继承 FR-MODEL-000B，逐条可测）：

1. 内置锁定版本 dsh，**不调用 PATH 中的全局 dsh**；
2. 独立 `DSH_HOME`，专用 profile `ai-novel-workbench`；
3. 不读取、修改或删除用户 `~/.dsh` 的配置、插件、会话和凭据；
4. 默认 stdio 子进程方式调用，不占用 dsh web 3080 端口；工作台自身端口 8790；
5. 小说项目、Story Bible、版本数据不存放在任何 DSH Home 内；
6. 安装与卸载不改变用户原有 dsh、Ollama、LM Studio 或其他模型服务；
7. "连接已有 dsh"（用户全局实例）仅作为实验性高级功能，必须通过版本检查 + Contract Test，不兼容时回退内置 dsh。

### 3.3 共享资产而非共享进程

工作台与用户的交互式 dsh **不共享进程、不共享 DSH_HOME，但共享项目级资产**——这是零冲突前提下实现"技能互通"的关键设计：

| 共享资产 | 位置 | 用户交互式 dsh 如何受益 | 工作台如何受益 |
|---|---|---|---|
| 入口指令 | `<项目根>/AGENTS.md` | dsh 会话在项目内启动时自动注入（预算 65536B） | headless 子进程自动注入 + 工作台直读展示 |
| 写作技能包 | 源目录 `skills/<name>/SKILL.md`；同步产物 `<项目根>/.dsh/skills/<name>/SKILL.md` | 同步后以项目级技能自动发现 | 工作台编辑源目录并通过 `POST /api/skills/sync` 或设置页同步；不手工编辑产物 |
| 小说数据 | `<项目根>/projects/{书名}/` | 用户在 dsh 里续写/审稿时直接读写 | 工作台主数据源（Markdown 为唯一事实源） |

用户在自己惯用的 dsh web（3080）里打开本项目时，获得与工作台一致的技能与数据；两个入口各自独立运行，仅可能发生**并发文件编辑**（见 C8 处理，9.4）。

### 3.4 版本锁定与升级（落地 FR-MODEL-000A）

- `workbench/vendor/dsh/package.json` 固定 `@deepseek-ai/dsh@0.1.0-rc.8`（精确版本号，不用 `^`/`~`）。
- **Contract Test 冒烟套件**（`workbench/tests/contract/`，dsh 升级前必跑）：
  1. `dsh --dump-config`（独立 DSH_HOME 下）退出码 0 且包含预期配置键；
  2. `dsh --profile headless` 最小任务（"请回复 OK"）成功返回；
  3. 技能发现断言：headless 任务内查询技能目录，`.dsh/skills` 下测试技能可见；
  4. 指令注入断言：AGENTS.md 中标记字符串出现在会话上下文（通过任务回答验证）；
  5. 隔离断言：运行前后用户 `~/.dsh` 哈希基线不变。
- **兼容矩阵**（`docs/compat-matrix.md` 维护）：Workbench 版本 × dsh 版本 × 验证状态 × 破坏性变更备注。
- dsh 仍是 rc 版本，**默认不追新**；新版发布后先在候选目录装新版本跑 Contract Test，通过后才更新 vendor 锁定。

## 4. 系统架构设计

### 4.1 总体架构

```text
浏览器（React 18 + Vite + TS SPA）
   │ HTTP/SSE
┌────────────────────────── FastAPI 后端（127.0.0.1:8790）──────────────────────────┐
│  API 层：项目管理 / 章节编辑 / 生成任务 / 审稿 / 技能 / 模型 / 工作流 / 统计        │
│  服务层：                                                                          │
│   ├─ ProjectService     项目与文件 CRUD、快照、回收站                              │
│   ├─ PipelineService    创作管线编排（章节 8 步循环、质量债分级、checkpoint）        │
│   ├─ ContextService     上下文包组装 + Token 预算裁剪（F18）                        │
│   ├─ ReviewService      逐项验收审稿、门禁调度、质检进度表                          │
│   ├─ IngestionService   章节摄取 → 追踪四件套                                      │
│   ├─ SkillService       技能注册/同步（skills/ → .dsh/skills）/作用域优先级          │
│   ├─ WorkflowService    工作流定义与执行（拖拽编排持久化）                          │
│   ├─ PromptRegistry     Prompt 资产注册制（id/version/taskType/contextPolicy）      │
│   └─ BudgetService      Token 用量统计与成本预估                                   │
│  引擎层（双引擎，按任务类型配置 engine: dsh-headless | direct-api）：               │
│   ├─ DshEngine        HarnessRuntime 实现：内置 dsh headless 子进程（主引擎）       │
│   └─ DirectApiEngine  HarnessRuntime 实现：OpenAI 兼容 API 直连（轻量/降级）        │
│  确定性层（零 LLM）：门禁脚本、字数/禁词/语言检查、摄取解析、统计                    │
│  数据层：Markdown 文件（唯一事实源） + SQLite（索引/任务/用量） + Git（版本化）      │
└───────────────────────────────────────────────────────────────────────────────────┘
   内置 dsh vendor + .workbench/dsh-home（隔离，见第 3 章）
```

### 4.2 核心架构思想

对齐 voocel__ainovel-cli 的『事实层确定，语义层自主』：

- **事实层（确定性）**：目录结构、状态文件、门禁脚本、Route 决策表全部零 LLM、可穷举测试。文件系统即事实源，任何 LLM 产物必须经确定性层校验后才允许落权威状态。
- **语义层（自主）**：大纲构思、正文生成、审稿意见交给引擎（dsh headless 为主）。语义层的每次裁定（如"该章节是否通过审稿"）落盘可回放（对齐 Arbiter 模式）。
- **闸口兜底**：不信任模型承诺——语言门、禁词门、字数门、记号泄漏拦截等由确定性脚本执行（oh-story 模式）。

### 4.3 双引擎决策表

| 任务类型 | 默认引擎 | 理由 |
|---|---|---|
| 大纲构思 / 正文生成 / 审稿 / 润色 / 拆书 | dsh-headless | 技能包（去AI味、审稿规则等）自动生效，指令注入保证一致性 |
| 结构化抽取（摄取/分类/标签） | direct-api（JSON mode） | 要求严格结构化输出，直连更可控、延迟低 |
| 轻量改写（<500 字小改，"修改模式优先"） | direct-api | 省 token、快 |
| Embedding / 检索 | direct-api | dsh 无对应能力 |
| dsh 不可用（vendor 损坏/Contract Test 失败） | direct-api 降级 | 工作台核心功能不因 dsh 而瘫痪 |

引擎配置存于模型配置页（第 5 章 FR-MODEL），按"全局默认 → 项目级 → 任务级"三级覆盖，任务级优先。

## 5. 核心功能模块划分

沿用基线 PRD 编号，标注优先级（P0=MVP，P1=Beta）。新增模块以 FR-AWS-*（AiWriteStudio3 增补）编号。

### 5.1 项目管理（FR-PROJ，P0）

- 创建/打开/归档小说项目；自动保存 + 版本快照；书架页（多书管理，参考 51mazi，MIT）。
- **开书即生成文件夹工作区**：创建项目时按资产种类自动初始化完整目录与空 md 文件（备忘录/大纲/设定/状态/章节，详见 9.1 目录规范）；文件内容可为空，供用户或 AI 逐步填充。
- **开书模板可自定义**：内置默认模板不可删除（可复制后修改）；用户可将调整后的目录结构「另存为模板」，下次开书可选用。
- **文件树手动管理**：前端支持新建文件/文件夹、重命名、删除（进回收站）、拖拽移动（详见 7.5）。
- 边界：所有数据在 `projects/` 下，不进任何 DSH Home。

### 5.2 Story Bible（FR-BIBLE，P0）

- 角色卡（9 要素，参考 human-novel-writer，MIT）、世界观实体、时间线、伏笔与未决事项台账。
- **来源分级**（EthanYoQ 方法论，仅思想）：每个事实字段标注来源（`author` 作者填写 / `model` 模型提炼 / `unknown` 待确认），审稿时 unknown 视为待核实。
- 与追踪四件套共用存储（9.2）。
- **卡片化视图与 AI 智能生成**见 5.16（设定卡片管理页）。

### 5.3 情节与大纲（FR-PLOT，P0）

- 灵感扩展（定向追问，陪练模式的理念，仅借鉴思想）；大纲生成（2-3 候选方案，用户确认后锁定）；**大纲冻结**（冻结后修改需走差异确认）；滚动规划（只细化近 2 卷弧，推进到时再展开，该模式借鉴自 voocel__ainovel-cli，Apache-2.0 可引思想）。

### 5.4 写作与编辑（FR-WRITE，P0）

- 场景/章节生成（章节合同驱动，第 8 章）；局部操作（改写/扩写/缩写/润色，选中即操作）；**生成上下文预览**（提交前展示将注入的上下文包与 Token 估算）；Ghost Text 候选（Tab 接受 / Esc 拒绝）；修改模式优先（<500 字小改走轻量路径）。

### 5.5 一致性与审稿（FR-REVIEW，P0）

- 一致性检查（数值算术/设定口径/细节连续三层，novel-skill-cards 模式）；**逐项目标审稿**：关键事件逐项标 已完成/未完成/待核实 + 正文证据引用，**待核实不算通过**（EthanYoQ 标准）；结果结构化落盘，支撑质检进度表。

### 5.6 技能与 Agent（FR-SKILL + FR-AWS-01/02，P0/P1）

- **FR-AWS-02 工作流编排（P1）**：拖拽式工作流编辑器（节点=任务类型+引擎+模型+技能），支持保存复用、批量产章；执行可暂停/恢复/断点续跑。

### 5.11 对话驱动与 Agent 体系（FR-AWS-05，P0）

**设计原则**：对话是主入口，但**不是唯一入口**——同一能力必须同时具备"对话式"与"功能页按钮式"双通道，二者共用同一套 Agent 定义与 Prompt 资产，行为一致。

- **对话为主入口**：Agent 调用、大纲/细纲/章节/设定的生成与修改均可在对话中完成。每轮对话 = 一次引擎调用 + 工作台组装的上下文包；会话状态机、会话列表、上下文裁剪由工作台维护（**不重写 dsh agent 循环**，见 6.7）。
- **功能页 AI 智能补全**：大纲页"AI 完善本卷"、设定页"AI 补全角色卡"、章节页"AI 续写/润色"等就地入口，与对话通道共用 Agent 与 Prompt 版本。
- **Agent 自定义**：用户可新建/编辑/复制/删除自定义 Agent；定义含名称、描述、系统提示词、绑定技能、模型、工具白名单、参数（温度等）；支持 **AI 辅助创建**（描述需求 → 生成定义草案 → 确认保存）。
- **内置 Agent 保护**：核心 Agent（创作助理（默认执行）/ 总编路由 / 规划 / 写作 / 审稿 / 上下文）标记 `is_builtin`，UI 默认隐藏且**不可删除**，但可复制为自定义后修改。新会话与意图未命中时由「创作助理」直接执行（不再落到只做分类的总编人格）。
- **技能自定义**：新建/编辑（SKILL.md 含 frontmatter）/导入/启用停用/AI 辅助生成；来源标记 `builtin`/`workbench_custom`/`imported`。
- **规则自定义**：全局级与作品级两级，与技能内置规则按优先级链（作者确认 > 作品级 > 全局 > 技能内置）解析；冲突显式提示并给出胜出依据。
- 所有自定义产物落盘为可版本化文件（`agents/`、`rules/`、`skills/`）。

### 5.12 Agent 级模型配置与对话内切换（FR-AWS-06，P0）

- **每个 Agent 独立配置模型**（provider + model）；未配置时按 任务级 → 项目级 → 全局默认 回退。
- 模型带**能力标签**（长文本 / 结构化 / 创意 / 低成本），配置页按擅长场景推荐——不同模型擅长场景不同，这是本设计的出发点。
- **对话面板可随时切换模型**，切换对下一轮生效；每次模型选择记入任务记录，可追溯。
- **注入方式（已实测校准，见 `docs/compat-matrix.md` §3）**：
  - 配置键 = `agent-default-model`（字段 `provider` + `model`）。
  - 可用 `--patch <file>` 按次注入：patch 为顶层 YAML 数组，`- id: agent-default-model` + `config: {provider, model}`。**注意 patch 整段替换 `config`，不做深合并，必须重述两个字段。**
  - **陷阱（务必遵守）**：`settings.yaml` 的用户层优先级**高于** `--patch`，且冲突时**静默胜出、无任何告警**。故工作台**不得**在 `.workbench/dsh-home/settings.yaml` 中固定写入 `agent-default-model`，模型选择一律走 `--patch` 按次注入；`settings.yaml` 只保留 provider 路由声明（`llm-pi-ai.providers.*`）。
  - 若未来需要强隔离，可备选"每 Agent 一份独立 DSH_HOME/settings"，但成本高，非默认路径。

### 5.13 角色成长与记忆引擎（FR-AWS-07，P0）

解决"模型生成的人物没有人味"的根因：**人不是静态设定，是会因遭遇而改变的**。

- **角色深度设定**：性格（多维特质 + 行为倾向）、核心价值观、说话风格（口癖/句长/称呼习惯）、关系网络（类型 + 强度）、**秘密与认知边界**（该角色不知道什么）。字段级来源标记 author/model/unknown。
- **角色视角记忆**：谁知道什么、何时知道、经何事件得知。用于防止**事实越界**（角色说出他不该知道的事）——这是"出戏"的头号来源。
- **状态机**：位置/持有物/伤势/心理状态/关系值/能力数值，字段级版本与来源。
- **成长触发**：章节事件 → 触发心态/立场/关系变化 Proposal（如遭遇背叛后信任值下降、对某事态度转变）。**所有变更经 Proposal 收件箱人工应用**，不静默改。
- **成长弧线可视化**：心理/关系/能力随章节变化曲线，变化点可跳转触发事件所在章节。
- **无依据突变拦截**：角色心态突变但正文无铺垫 → 审稿判不通过并提示补铺垫。
- **按需注入**：ContextService 仅注入本章涉及角色的性格要点 + 当前状态 + 近期相关记忆，而非全量角色卡（控预算）。
- 审稿时校验言行不超出角色记忆边界（与 5.5 一致性检查协同）。

### 5.14 本地向量检索（FR-AWS-08，P1）

- **本地嵌入模型**：首次下载到本地后**离线推理**，不依赖云 API；模型与向量库落 `.workbench/models/` 与 `.workbench/vector/`，**绝不写入任何 DSH Home**。
- 向量库与现有 SQLite 索引共存（优先 sqlite-vec 等轻量方案）。
- 索引对象：章节正文、Story Bible 条目、拆书事实卡、技能与规则文档。
- **增量索引**（章节应用落盘后自动入索引）+ **全量重建**。
- 召回结果注入上下文包第 8 级优先级（见 8.3）；上下文预览显示命中条目与相似度（可审计）。
- 降级：模型下载失败时退化为纯 FTS 关键词检索，功能不中断。
- 说明：dsh 无 embedding 能力（见 6.7），故本项纯自建；Embedding 由本地模型或 direct-api 提供。

### 5.15 UI 设计系统与长时间工作适配（FR-AWS-09，P0）

- **设计系统 token 化**：色彩/字体/间距/圆角/阴影/层级全部 token 化，禁止散落硬编码色值。
- **去 AI 感**：明确规避通用 AI 生成风格——紫色渐变、滥用玻璃拟态、emoji 充作图标、居中大标题堆叠、无差别卡片网格。视觉定位为**专业写作工具**（编辑器的克制、纸张的沉静），而非营销页。
- **多主题**：至少 亮色 / 暗色 / 纸感阅读 三套，可持久化；支持跟随系统暗色与"减少动效"开关。
- **护眼模式**：色温调节、对比度调节、字号/行高/字距/页宽可调、专注模式（隐藏侧栏与干扰元素）。面向**长时间写作/阅读**场景。
- **阅读态**：编辑态（三栏）↔ 阅读态（沉浸单栏）切换；阅读视图限制页宽、优化段间距与行高，适配长时间阅读。
- **无障碍**：主要流程（切章/保存/切换主题/唤起对话）全键盘可完成；焦点可见；对比度达 WCAG AA。

### 5.16 设定卡片管理页（FR-AWS-10，P0）

以**卡片化视图**集中呈现 `设定/` 下各类设定（人物/世界/势力/物品/技能/场景/伏笔），支持 AI 智能生成与双向同步。**事实源仍是 Markdown**，卡片只是视图层。

- **双层数据策略（解析稳定性兜底）**：Markdown 完全自由书写（用户选定的"纯自由"），卡片由确定性骨架 + AI 补字段 + 缓存指纹三层构建：
  1. **确定性骨架**：以解析器提取标题层级（人物用 `#`/`##` 人名、伏笔用表格行、世界观用目录小节）等**零 LLM 机械提取**的结构化底座——即使 AI 解析失败，卡片仍能保证"有多少条、叫什么名"不错。
  2. **AI 字段补全**：对骨架中缺失的字段（性格/身份/关系/说话风格等）由 direct-api 结构化解析补全，产出带来源标记（author/model/unknown）的字段。
  3. **缓存指纹**：对文件内容做 hash 作为解析缓存键；内容未变则复用缓存，避免重复解析。解析结果存 `.meta/asset_cards.json`（可重建缓存，非事实源）。
- **AI 智能生成**：卡片页"AI 完善/生成"按钮（对话通道 + 就地按钮双通道，共用 Agent 与 Prompt 资产，见 5.11）；生成产物的字段带来源标记，**全部经 Proposal 收件箱人工应用**后才写回 Markdown，不静默落盘。
- **双向同步**：Markdown 手改 → 刷新卡片（解析缓存失效重解析）；卡片编辑 → 以 diff 形式写回 Markdown（保自由书写，只改对应字段段）。冲突走 9.4 外部修改检测。
- **单条卡片支持新建**：手填或 AI 辅助生成一条，生成对应 Markdown 片段追加到对应设定文件。
- **高亮色标记（重点角色视觉区分）**：卡片可指派高亮色，用于标记**重点角色/重点实体**（如主角、核心反派、关键道具），便于在卡片列表中一眼区分主次。
  - 交互：单条卡片可指派 / 更改 / 清除高亮色；工具条的「高亮色」为当前选中色板，选中后点击卡片即着色。
  - 色板：走设计系统 token 定义的有限色板（非自由取色），保证亮色/暗色/护眼三主题下均可辨识（含对比度校验）。
  - 持久化：高亮状态存 `.meta/asset_cards.json`（与解析缓存同处，属视图层元数据，**不写入 `设定/*.md`**，避免污染自由书写的正文内容）。
  - 筛选联动：可「仅显示高亮」过滤重点角色，配合搜索使用。
  - 与来源标记独立：高亮色是视觉标记，不参与 author/model/unknown 来源分级，也不影响审稿判定。

### 5.17 字数里程碑提示（FR-WRITE 扩展，P0）

编辑器内实时显示当前章节字数达成提示（图 1 红色方框效果的装饰层，**只读展示，不写入正文、不落盘**）。

- **固定阈值 + 合同进度双轨**（默认每 500 字一个节点，阈值可配）：
  - 「已满 500 / 1000 / 1500 N 字」里程碑徽标；
  - 「距本章合同字数预算」进度（`已满 1500 字 · 预算 3000 · 50%`）；无合同/无预算时仅显示累计字数。
- **数据来源**：字数由 frontmatter 的 `字数` 字段 + 实时编辑 diff 计算（保存时落 frontmatter）；预算读当前章节合同（`.meta/`）。
- 随输入实时刷新；阈值与样式走设计系统 token，可暗色/护眼适配。

@runtime_checkable
class HarnessRuntime(Protocol):

### 6.3 headless 调用协议（DshEngine 实现，**已实测校准**）

> 本节已按 2026-09-19 实测结论修订（证据见 `docs/compat-matrix.md`）。原设计的部分假设与实测不符，已修正。

- 调用形式：`subprocess` 执行 `<vendor>/node_modules/.bin/dsh --profile headless "<任务指令>"`（Windows 实际为 `dsh.cmd`），工作目录 = 项目根（保证 AGENTS.md 与 `.dsh/skills` 生效），环境注入 `DSH_HOME=<项目>/.workbench/dsh-home`。`--profile` 为**必填**（裸 `--dump-config` 直接报错）。
- **stdout/stderr 协议（实测）**：
  - stdout = **最后一条非空 assistant 文本** + `\n`；**无日志、无流式、无工具输出**
  - stderr = 成功时为空；失败时为单行 `dsh: <CODE>: <message>`
  - 退出码 = 成功 0 / 失败 1（用法错误亦为 1）
  - **陷阱**：失败时 stdout 仍可能是一个**空行** → **不可用"stdout 非空"判定成功**，必须用 `退出码 == 0 且 stderr 为空` 判定
  - 无 JSON / `--output` 结构化输出模式
- **产物落盘**：dsh headless **不会**自动把产物写文件。工作台 SHALL 在任务指令中**显式要求模型使用文件工具写入指定路径**，stdout 仅回一个简短确认（实测可行）。这与工作台"事实源落盘"设计一致，也是解析最稳的路径。
- **任务指令模板**（PromptRegistry 管理）固定结构：`任务类型 + 上下文包文件路径 + 输出文件路径 + 硬约束 + 显式落盘指令`。
- **调用边界（2026-09-22 修订）**：以上限制仅适用于一次性 headless CLI。工作台对话使用独立 `ai-novel-chat` profile 和 stdio runner，直接复用锁定版 dsh 的 Agent API：同一会话 `followup()`，冷恢复 `agents.resume()`，原生记录位于独立 DSH_HOME 的 `chat-sessions/`。正文通过原生 `assistant/chunk` 经 SSE 实时输出；不再把每轮对话作为一次新的 headless 调用。工作台以消息 ID 和持久接收确认补送未送达历史，补送内容为历史材料，不重执行旧任务。
- 超时（默认 600s 可配）/ 取消（进程树终止）/ 失败重试（指数退避，最多 2 次）/ 每任务独立 checkpoint（可断点续跑）。
- 并发控制：同一项目同时最多 2 个 headless 任务（可配），避免文件写冲突。
- 会话产物：每次调用都会在 `.workbench/dsh-home/sessions/` 落一个持久化会话文件（实测确认，数据在盘但**无 CLI 入口引回**），提供清理任务（保留最近 N 条，默认 50）。

### 6.4 Provider 投影（单向，工作台 → 内置 dsh-home）

- 工作台模型配置页维护 `ModelProviderProfile`（字段沿用基线：provider_id / display_name / source / base_url / **models[]** / capabilities / secret_ref / timeout_seconds / retry_policy / enabled）。
  一个供应商可配置**多个模型**（每个模型含 `id` / `name` / `context_window` / `max_tokens`，后两项留空则用默认值 131072 / 8192），投影时逐模型写入。
- 保存、启用、停用或删除供应商后，自动把启用中的 provider **单向投影**为 `.workbench/dsh-home/settings.yaml` 中的 provider 条目；启动时也按数据库修复旧投影。已有原生对话工作进程在下一轮检测投影版本变化后重建，并从持久会话恢复。反向只读。**绝不写入 `C:\Users\30332\.dsh`**。
- **投影范围限定（实测约束）**：settings.yaml 中**只投影 provider 路由声明**（`llm-pi-ai.providers.*`：displayName / api / baseURL / apiKeyEnv / models），**不得投影 `agent-default-model`**——该项会静默压过 `--patch`，导致 per-Agent 模型配置失效（见 5.12 与 compat-matrix §3）。模型选择统一由 `--patch` 按次注入。
- **全局默认模型**：存 `.workbench/settings.json` 的 `engines.default_provider` / `engines.default_model`（三级覆盖的「全局级」），运行时由 `provider_service.default_target()` 解析为本次任务的 provider/model，再经 `--patch` 注入；**仍不写 `agent-default-model`**。默认指向的供应商被停用或删除时自动清空并回退到第一个启用的供应商。
- Key 以 `apiKeyEnv` 引用（如 `WB_FLUXL_API_KEY`），明文写入同目录 `.credentials.yaml`（已 gitignore），不落进 settings.yaml。投影只替换工作台拥有的 provider 路由和 `WB_` 凭据，保留独立 dsh-home 内其他设置。
- `source=dsh_builtin` 的条目：允许用户显式导入其全局 dsh 的**非敏感**配置（baseURL/模型名），Key 必须重新录入工作台安全存储，不自动复制（FR-MODEL-002A 继承）。

**一律复用（不重写）**：

| dsh 能力 | 包 | 工作台用法 |
|---|---|---|
| Agent 循环与工具调度 | `dsh-agent-loop`、`dsh-tools` | 不重写；工作台只组装任务与上下文 |
| 技能发现与加载 | `dsh-skill-filesystem`（rank 100 `<projectRoot>/.dsh/skills`） | 复用格式与加载器；工作台只做管理 UI 与同步 |
| 指令注入 | `dsh-agent-instructions`（AGENTS.md，预算 65536B） | 复用注入机制；规则优先级链是工作台上层编译逻辑 |
| 会话持久化 | `dsh-session-persistence` | 复用 |
| Token 计量 | `dsh-token-meter`、`dsh-session-stats` | 单会话数据源；工作台只做跨项目聚合仪表盘 |
| 上下文压缩 | `dsh-compaction`（超限后补救） | 与工作台 ContextService（组装期预防）互补叠加 |

**必须自建（dsh 无此能力，或有但不满足需求）**：

| 需求 | dsh 现状 | 自建理由 |
|---|---|---|
| 对话交互层 | headless CLI 为单次任务；原生 Agent API 支持持续会话、流式事件和冷恢复 | 工作台提供持久运行、小说权限、批准/问题卡和 SSE 展示；模型与工具循环由 dsh 负责 |
| 工作流可视化编排 | `dsh-workflow` 为模型编写的 JS 脚本式编排，已知限制：**无日志化、无检查点、进程重启无法继续、无已保存或嵌套工作流** | 无法满足"拖拽编排 + 批量产章 + 断点续跑" |
| Agent 定义管理 | `dsh-agent-presets` 存在但耦合 cordis 内部（`agent.cordis.yml`），信任级别等同 shell | 违反"业务层不触碰 dsh 内部"红线；改用工作台声明式定义 |
| 本地向量检索 | 安装树内**无任何 vector/embedding/memory/rag 包** | 纯自建（用户侧 recall-plugin 为第三方、profile 级，隔离原则下不可依赖） |
| 文件/文件夹初始化与文件树管理 | `dsh-tool-fs`、`dsh-fs`、`dsh-tool-str-replace-editor` 是 **Agent 会话内的文件操作工具**（供模型读写文件），非产品级"工作区模板初始化"能力 | **不重合**：开书模板、文件树 UI、新建/重命名/删除/拖拽均为工作台自有产品功能。仅需处理**双入口并发写**（用户在 dsh 会话改同一文件 → 走 9.4 的 mtime+hash 检测 + diff 弹窗） |
| 角色成长/记忆 | 无小说领域模型 | 纯自建 |
| UI 设计系统/主题/护眼 | `dsh-client-ui-theme` 属 dsh 自有 Web UI | 工作台 UI 独立 |

**须实测确认（不得假设，M0 完成）**：① headless 会话续接能力；② `--patch` 运行时指定模型能力（per-Agent 模型注入依赖此）；③ headless stdout 与产物落盘协议。三项结论写入 `docs/compat-matrix.md` 并据此冻结 M2/M6 实现方式。

### 6.8 对话运行、权限与恢复（2026-09-24 实现）

对话路径使用 `engine/dsh_chat.py` 与 `dsh_chat_runner.mjs` 适配 vendor 原生 Agent API，持续保存同一个原生会话；仍通过 `dsh_paths.py` 调用锁定的内置运行时，使用独立 `.workbench/dsh-home`。6.3 的 headless 单任务协议适用于其他生成任务，不再描述对话执行。对话不启用 dsh 自带终端、通用文件写入或子 Agent 工具，所有书稿变更通过工作台工具桥及统一文件变更服务。

**权限事实源**为每个会话的 `permission_mode` 和独立 `discussion_only`，每轮开始时冻结快照。新对话默认为 `auto`、关闭只讨论；设置页的“对话”项只影响之后创建的会话。运行中调整权限会显示“下一轮生效”，不会自动回答已经出现的批准卡。明确的只讨论、只审稿要求仍限制本轮书稿工具，“继续”“按方案来”不会撤销已有写入权限。

| 模式 | 当前小说中的行为 |
|---|---|
| `ask` 请求批准 | 所有书稿变更展示路径、操作和归一化后的实际差异，作者批准后继续当前工具调用 |
| `auto` 帮我批准 | 新建与局部修改自动执行；删除、移动、整份已有文稿覆盖请求批准；精确替换整个正文也视为覆盖 |
| `full` 完全访问 | 本书内受支持的 Markdown 文稿操作自动执行，包括可撤回的删除、移动和覆盖 |

三档均执行先读后改、版本比对、章节硬门禁、快照和撤回检查。批准绑定内容与文件版本，版本变更会使旧批准失效；重复回答或工具调用不重复写入。只讨论允许保存对话及本书记忆，不允许改动书稿。工作台登记的小说保留原目录，第三方参考目录只读；隐藏路径、跨书路径及链接绕过被拒绝。

迁移规则：旧只读会话 → `ask + discussion_only`；旧收件箱模式 → `ask`；旧直接修改 → `auto`；未知旧权限 → 只讨论。旧会话不会自动获得 `full`。

**消息与交互持久性**：工作台消息 ID 对应稳定的原生消息 ID；原生持久化确认后才记 `dsh_delivered`。此前未送达作者消息会作为带原角色与失败状态的历史材料补送，不重新执行旧指令。原生已入队但未进入模型历史的中断消息在恢复时转为历史，清理旧待执行队列。自动附带的不存在或不支持格式文件改为上下文警告，作者正文正常投递；明确指定的无效文件仍报错并保留原消息。冷恢复失败明确报错，不静默创建空会话。

`ask_user_question` 提供 1–3 个问题，支持单选、多选和固定“其他”；其他输入必须非空。问题与批准共用磁盘交互记录，回答作为原工具调用结果返回。任务在 `waiting_input` 时继续占用本会话的活动槽，等待作者不消耗模型执行超时，且不持有数据库事务或文件锁。刷新、切页和 SSE 重连可恢复卡片。后端重启把未完成任务标为中断，保留回答、差异和已经写入的文件；作者继续时先核对上一轮实际状态。

**本书记忆**：书目录 `.meta/chat-memory.json` 为事实源，保存作者明确确认的事实、偏好和决定以及来源消息、旧版本、删除状态。提取采用保守的确定性规则；含糊回答、AI 建议和暂定内容标为待确认，不注入新对话。面板支持查看、更正、删除和来源跳转；明确的新更正替换同一主题的旧决定。与项目/设定文件明确字段的差异会显示待核对提示，记忆本身不触发书稿修改。上下文按预算装入已确认记忆，并在“本轮引用”中显示来源。书与书隔离，工具批准不作为创作记忆继承；损坏的可选记忆文件给出警告，不阻断作者消息。

**标题与过程**：首条作者消息保存后启动独立、无工具的轻量标题任务，使用本会话解析的模型及原有标题提示词，超时 30 秒、无自动重试。正文失败不阻断标题，正文先结束时前端仍短轮询标题状态；人工改名会使旧任务结果失效。失败保留临时标题，可用“AI 重新命名”重试，旧标题默认保留。过程记录包括实际处理角色、已注入/加载的技能、模型阶段、工具参数/结果、时间与耗时。角色选择单独标识，不虚构子 Agent 调用。正文使用真实文本增量；历史与实时共享过程数据、事件序号和快照，重连去重。

**存储与接口**：`.workbench/chat/sessions/` 保存会话与消息快照，`.workbench/chat/runs/<run_id>/` 保存请求、事件和交互，SQLite 为相应运行/交互的可恢复索引；项目索引重建时按书稿路径校验归属。文件变更沿用 `workspace_changes` 日志与快照恢复机制。

- `POST /api/chat/runs/{run_id}/interactions/{interaction_id}/respond`：结构化答案、批准或拒绝；校验归属、活动状态和幂等性。
- `GET /api/projects/{project_id}/chat-memory`；`PATCH` / `DELETE /api/projects/{project_id}/chat-memory/{memory_id}`：本书记忆管理。
- `POST /api/chat/sessions/{session_id}/title/regenerate`：异步重新命名。
- 现有运行快照和 SSE 增加 `interaction`、`context_warning`、阶段步骤及上下文来源；旧 `mode/auto_apply` 保留兼容映射。

验收命令：`python -m pytest workbench/backend/tests -q`；前端目录运行 `npm test`、`npm run build`。浏览器验收可运行 `python -m workbench.backend.tests.chat_acceptance_server`：仅监听 8790，使用独立 `.workbench/chat-acceptance` 测试书、vendor 原生运行时和确定性本地模型，不调用真实供应商。生产启动不加载该测试适配器。

### 7.4 交互原则

- **人控决策、AI 加速**：方向类决策永远给候选让用户选，绝不静默代决；正文只有明确指令才生成，且默认标"待人工精修"（陪练原则，仅借鉴思想）。
- **粗稿 ≠ 终稿**：生成产物带状态标记，进正文需经收件箱应用。
- **可解释**：每次 AI 行为可追溯（任务记录、Prompt 版本、上下文快照）。
- 凭据只显示服务商名 + 掩码 Key；暗色/亮色主题；基础键盘可达性。

### 7.5 文件树与文件/文件夹管理

开书生成的工作区（9.1）在左栏以文件树呈现，用户可直接管理：

| 能力 | 规范 |
|---|---|
| 目录结构 | 按资产种类分组展示（备忘录/大纲/设定/状态/章节），与磁盘结构一一对应 |
| 新建 | 支持新建文件与文件夹；新建文件默认 `.md`，可指定父目录 |
| 重命名 | 就地重命名；章节文件重命名时校验 `第NNNN章.md` 命名规范，不符合则提示修正 |
| 删除 | **按内容分策略**：空文件（正文去空白后为空，含仅有 frontmatter 未写正文的章节）**直接物理删除**；非空文件进回收站（`.workbench/trash/`）可恢复。文件夹：其下全部为空则物理删除，否则整个文件夹进回收站 |
| 拖拽移动 | 拖拽调整层级与归属；跨分组移动需二次确认（避免误把设定拖进章节） |
| 模板操作 | 「另存为模板」将当前目录结构存为自定义开书模板；内置模板不可删除，可复制后修改 |
| 状态徽标 | 章节节点显示三状态徽标（草稿/完成/发表）；空文件以浅色区分 |
| 外部变更 | 磁盘上被外部（如 dsh 会话）增删改的文件，经索引重建后反映在树中；冲突走 diff 弹窗（9.4） |

**一致性约束**：所有文件树操作与模板初始化共用同一套原子写与索引重建逻辑；树上的任何变更都不得绕过 9.4 的并发与外部修改检测。

**空文件判定与删除安全**：

1. **判定口径**：`正文内容（剔除 YAML frontmatter）去除首尾空白后长度为 0` 即视为空文件。模板初始化的空 md、以及只写了 frontmatter 未写正文的章节，均属此列。
2. **物理删除不可恢复**，故删除前须有轻量提示（Toast：「已删除空文件 X」），不弹确认对话框（空文件无内容可丢）。
3. **非空文件一律进回收站**，可恢复；批量删除混合选择时，空文件物理删除、非空文件进回收站，并在结果提示中分别明示去向。
4. **被引用文件保护**：若空文件已被章节合同、审稿报告或 `.meta/` 记录引用，则降级为进回收站（不物理删除），避免悬空引用。
5. 物理删除同样须刷新索引与文档树，并记入操作日志（可追溯）。

## 8. 小说创作流程优化策略

### 8.1 章节生产 8 步循环（综合 huahuakandaima + voocel 的可引入资产；EthanYoQ 仅思想借鉴）

> 合规注：huahuakandaima（MIT）、voocel（Apache-2.0）可引入；EthanYoQ 主应用为 GPL，其"待核实不算通过"标准属审稿方法论思想，独立实现。

```
LOAD    → ContextService 组装上下文包（8.3），落盘为任务输入快照
CHECK   → 确定性层校验前置依赖：大纲已冻结/文风样本存在/知识门控通过
          （缺失即阻断并提示补齐，tianming 依赖门控模式）
CONTRACT→ 生成章节合同：情节点清单+字数预算+章尾钩子类型+涉及实体；
          用户确认（或沿用模板默认）后冻结为验收标准
DRAFT   → 引擎生成（dsh-headless 主）；产出先进 Proposal 收件箱
REVIEW  → 双门禁：确定性脚本（字数/语言/禁词/记号泄漏）硬门 +
          模型审稿（逐项对照合同，待核实不算通过）
REVISE  → 未过项自动生成修改指令回灌引擎；最多 2 轮，超轮次转人工
UPDATE  → 用户应用后：IngestionService 章节摄取 → 更新追踪四件套
          （摘要/实体/关系变化/伏笔增删/时间线），checkpoint=commit
DECIDE  → 章节状态流转（草稿→完成），质检进度表更新，质量债登记
```

每步落 checkpoint（voocel 模式），中断后可从精确步恢复。

### 8.2 质量债分级（自定分级；仅借鉴非阻塞生产链思想）

> 合规注：原标注来源 ExplosiveCoderflome 为 **AGPL**（最强传染，含网络服务条款），**不可引入代码**。分级思想（章级瑕疵放行、仅 replan 级停链）属方法论，工作台自定分级与实现。

### 8.3 上下文包优先级组装 + Token 预算（自定；仅借鉴优先级方法论）

**设计要点**：

1. **静态设定（`设定/`）与动态状态（`状态/`）分离**——设定是"按需查"，状态是"每章必读"；ContextService 依此区分注入策略（见 8.3），避免把全量设定塞进上下文。
2. **文件内容可为空**——初始化只建骨架，用户或 AI 逐步填充；空文件不参与检索索引。
3. **章节命名** `第NNNN章.md`（四位零填充，保证排序稳定）；章节三状态（草稿/完成/发表）记于 frontmatter。
4. **`拆书/`、`.meta/` 为可选生成**——拆书按需创建；`.meta/` 随首次生成任务自动创建。
5. **模板可自定义**——用户可将调整后的目录结构「另存为模板」存于 `templates/`，下次开书可选用；内置默认模板不可删除，可复制后修改。
6. **前端文件树支持手动管理**——新建文件/文件夹、重命名、删除（进回收站）、拖拽移动；所有操作与初始化模板同走原子写与索引重建。

### 9.2 追踪四件套（数据契约）

落位于 `状态/` 与 `设定/`，与 9.1 目录规范一致：

| 文件 | 结构要点 | 维护方式 |
|---|---|---|
| `状态/时间线.md` | 事件行：`章节 | 故事内时间 | 事件 | 依据原文` | 章节摄取自动追加 + 人工修订 |
| `状态/角色状态.md` | 位置/持有物/关系/认知/伤势/心理/关系值，每字段带来源标记（author/model/unknown）与版本 | 摄取生成变更 Proposal，人工应用 |
| `状态/资源账本.md` | 金钱/物品/能力数值表（防穿帮物价表，Wooooooooood 模式） | 摄取更新 + 数值算术校验 |

> 静态设定（`设定/` 下其余文件）与动态状态（`状态/`）分离：前者按需查，后者进每章必读集。

### 9.3 SQLite 索引表概览

`projects / chapters / proposals / tasks(引擎任务与状态) / reviews(逐项审稿记录) / quality_debts / token_usage(任务级用量) / providers / skills / workflows / prompt_registry / snapshots / templates(开书模板) / assets(设定与状态文件索引 + 设定卡片解析缓存引用) / chapter_contracts(章节合同索引)`。SQLite 仅为索引/缓存，**重建即可恢复**，事实永远在 Markdown + JSON。

### 9.4 并发与一致性

- 写入一律原子写（临时文件 + rename）；章节级文件锁（`.meta/locks/`）。
- 外部修改检测：编辑器打开期间比对 mtime+hash，检出外部改动（如用户在 dsh 侧修改）→ 弹差异对比，三方选择（保留我的/采用外部/合并）。
- Git 提交点：章节 DECIDE 完成、大纲冻结、Story Bible 应用 Proposal 时自动 commit（可配）。

### 9.5 Git 工作流

- 项目根 `git init`（解决 dsh projectRoot 分裂，C5）；`.gitignore` 覆盖 `.workbench/`、`node_modules/`、模型 Key 相关文件；不强制远端，支持用户自配远端备份。

### 9.6 凭据安全（FR-MODEL-003 继承）

- Key 存储于 `.workbench/secrets.json`（Windows DPAPI 加密，`keyring` 库），不入 Git、不入导出包、不入日志与 Prompt；UI 掩码显示；`模型API.md` 中的明文 Key 建议迁移后删除该文件（实施期人工操作，不代删）。
- 日志脱敏：Authorization 头、apiKey 字段一律过滤。

### 9.7 隔离完整性自检（冲突防线兜底）

- 首次启动记录基线：`C:\Users\30332\.dsh` 下 settings.yaml / profiles/ / .agent-presets/ / storages/workspace.json 的 SHA-256 与 mtime。
- 每次工作台会话结束自检比对；不一致 → 高亮告警（不自动修复用户侧文件），并给出"最近可能原因"报告。
- 全局 npm 列表快照同理（验证未安装任何新全局包）。

| # | 检查 | 方法 |

### 11.2 Contract Test（3.4 套件，dsh 升级门禁）

`--dump-config`、headless 最小任务、技能发现断言、AGENTS.md 注入断言、隔离断言，5 项全过才允许换版本。

### 11.3 确定性层单测

门禁脚本（字数/语言/禁词/记号泄漏）用样章正反例穷举；ContextService 裁剪策略用固定语料断言优先级顺序与降级记录；摄取解析器用样章断言四件套字段。

### 11.4 Guardrails 快照测试（方法论借鉴 EthanYoQ；其主应用为 GPL，**仅用思想，不复制其测试代码**）

对引擎适配层：固定输入（任务指令 + 上下文快照）→ 断言输出文件结构 / 状态变更 Proposal 的 schema 快照一致；模型输出可变部分先经确定性归一化再快照。

### 11.5 端到端冒烟

`建项目 → 灵感追问 → 大纲候选确认 → 冻结 → 生成第 1 章（8 步全循环）→ 审稿 → 应用 → 摄取 → 导出正文` 全链路脚本化，M2 起每里程碑必跑；含双引擎切换用例（中途禁用 dsh）。

### 11.6 性能基准

编辑器打开 200 章项目首屏 < 2s；上下文包组装 < 1s；headless 任务取消响应 < 3s。

### 13.1 法律判断基石

著作权**保护表达、不保护思想**。据此分四级：

| 层级 | 含义 | 适用 |
|---|---|---|
| **T1 直接引入** | 复制代码，保留版权声明 | MIT / Apache-2.0 |
| **T2 适配改造** | 复制后改写（提示词/模板/技能文本），保留声明 | MIT / Apache-2.0 |
| **T3 独立实现** | **只借鉴思想，不复制任何表达** | GPL / AGPL / CC-NC-SA / 无证 |
| **T4 禁用** | 不接触其具体表达 | 无证项目的代码与文本 |

架构思想、设计模式、流程概念（如 Proposal 收件箱、上下文包优先级、质量债分级）属思想范畴可自由借鉴；实现代码、提示词原文、SKILL.md 文本一律自写。
